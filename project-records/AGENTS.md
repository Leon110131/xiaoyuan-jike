# 教练轻记后续开发约定

继续开发前先读 `项目当前版本.json` 和 `体验测试与正式版同步台账.md`，使用索引指向的当前源码。子目录内的开发要求仍需遵守。

2026-10-20 台账整理补充：同时读取索引 `formalSyncPlan` 指向的 `正式版接入核对清单.md` 和 `formalSyncRegistry` 指向的逐条登记。`formalPendingChanges` 是历史追溯列表，包含部分被覆盖需求及验证证据，不能逐行重放。以最新有效行为、覆盖关系和模块依赖顺序为准；被用户弃用的版本方案不重新纳入。

每次后续交付须更新原始台账、逐条登记及当前版本索引，运行 `node work/verify-formal-sync.cjs`；校验失败先解决再交付。文档整理不代表正式合并；正式提交、验证证据、真机及部署状态须分别记录。未收到用户通知体验测试结束，不提前启动正式接入。两版存储作用域不同，不以复制存储键或体验限制覆盖正式设计。

用户于 2026-10-15 确认：已上传体验版 v0.1，预计测试 1–3 个月。测试期间任何功能修改、删除、新增及漏洞修复都必须持久记录，供首次正式上线版本 v0.1 同步。正式开发基线目前编号 v0.4.1，与用户计划的正式发布版本 v0.1 是不同概念。

每次交付更新必须更新同步台账：记录需求日期、变更类型、行为变化、源码路径、验证结果、体验版交付版本及正式基线同步状态。不能只依赖聊天记忆；未实际合并和验证不得标记“已同步”。体验专属改动与正式版共用改动须分别标明，避免把体验版不收费、不接云、无邀请等限制直接覆盖正式版设计。

用户自行录入数据、存储键和备份兼容性是每次升级的检查项；不得以重置缓存解决升级问题。涉及数据结构须记录迁移和回滚方案。

正式上线前逐项核对台账，合并适用变更并验证。未来云服务、真实身份权限、支付及跨版本数据迁移只能按实际实现和验证情况说明，不得把开发基线称为已具备正式上线条件。

已交付的归档和压缩包保持原样；后续修改在明确的新版本源码中进行，并更新当前版本索引、变更记录和交付校验。

2026-10-20 v0.2.32整理补充：当前有效候选及参考分类见索引formalSyncSummary，历史验证另见formalSyncEvidenceIndex。更新台账/逐条登记/索引后运行 `node work/refresh-formal-sync-summary.cjs`、`node work/refresh-formal-sync-diff.cjs`，最后运行 `node work/verify-formal-sync.cjs`；不要手工维护两份候选清单，部分覆盖条目必须保留未被替代的行为。
